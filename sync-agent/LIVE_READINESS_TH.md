# ขอบเขตซิงก์ข้อมูลจริงและผลสำรวจ

อัปเดตหลังผู้ใช้อนุมัติทดสอบครบชุด: ดู [ผลทดสอบข้อมูลครบชุด](HISTORY_COPY_RESULTS_TH.md) ซึ่งผ่าน1,438ลูกค้า/4,075บิลขาย/21ใบคืน/12,491บรรทัดและreplay/restartแล้ว เอกสารด้านล่างเป็นผลสำรวจก่อนสร้างโมดูล history ใหม่ ขอบเขต production writer/API ยังไม่เปิด

24 ตุลาคม 2026 เวลา 17:53 น. ประเทศไทย — สำรวจสองฐานแบบอ่านอย่างเดียว ไม่มีการนำเข้าหรือแก้ข้อมูลจริง

เป้าหมายตามผู้ใช้: Ada เป็นระบบขายต้นทาง ส่วน SCCRM เป็นหน้าจอจัดการสมาชิกและค้นประวัติที่ยืดหยุ่นกว่า เก็บลูกค้าและประวัติเดิมจาก Ada ใน Supabase และส่งการสร้าง/แก้ไขข้อมูลฝั่ง SCCRM กลับไปเฉพาะสิ่งที่ Ada รองรับ คงข้อห้ามลบข้อมูล Ada และไม่รบกวน Shopee

## แบบข้อมูลที่ควรใช้

1. เก็บทะเบียน Ada แยกตาม source + รหัส Ada เดิม ครบทั้งมี/ไม่มีเบอร์ ห้ามใช้เบอร์เป็น primary key หรือบังคับสร้างบัญชีล็อกอินให้ทุกรหัส คงรหัสซ้ำเบอร์เป็นคนละ record จนยืนยันการผูก ไม่รวมลูกค้าเดิมทิ้ง
2. เก็บความสัมพันธ์รหัส Ada กับสมาชิก SCCRM แบบชัดเจน สาม mapping ที่ผู้ใช้เลือกไว้ก่อนหน้ายังคงเป็นรหัสที่อนุมัติ การนำเข้ารหัสอื่นไม่ได้อนุมัติให้รวมประวัติเข้าบัญชีออนไลน์จากชื่อ/เบอร์อย่างเดียว
3. ประวัติซื้อยึด identity สาขา + เครื่องขาย + เลขเอกสาร + ประเภทเอกสาร และเลขบรรทัด เก็บ SKU ชื่อสินค้า หน่วย จำนวน ยอด วันเวลา และสถานะบิล/คืนสินค้า รหัสลูกค้าทั่วไปและบิลไม่มีรหัสต้องไม่กลายเป็นประวัติส่วนตัวของคนใด
4. การนำเข้าประวัติเดิมไม่สร้างแต้มใหม่จากยอดซื้อซ้ำ คะแนนเดิมของ Ada ต้องเก็บที่มาแยกจากคะแนน SCCRM และการเปลี่ยนแปลงอนาคตใช้รายการเพิ่ม/ลดที่กันซ้ำ
5. Supabase -> Ada: สร้างใหม่โดยไม่ทับรหัสเดิม; แก้เฉพาะ field ที่ยืนยันว่า Ada รองรับและ mapping ถูกต้อง เช่นชื่อ/เบอร์/อีเมล หากสองฝั่งแก้ขัดกันใช้ Supabase ตามคำตอบเดิมของผู้ใช้ เก็บ before/after และตรวจ concurrent change ก่อนเขียน ค่าว่างไม่ล้างข้อมูลเก่า
6. ข้อมูลเพิ่มของ SCCRM ที่ Ada ไม่มีช่องรองรับเก็บใน Supabase คงไว้ ไม่ตัดทิ้งให้พอดี Ada; ฟิลด์ที่แปลงภาษา/ขนาด/ความหมายไม่ได้ต้องค้างรอทบทวน ไม่เขียนค่าที่เสียความหมาย

## อะไรผ่านแล้ว และอะไรยังไม่ใช่หลักฐานพร้อมจริง

ผ่านแล้ว: กลไกสองทางบนสำเนา 31 integration cases, Windows service restart/healthy, retry/idempotency/conflict/blank handling, ข้อมูลเดิม 11 แถวไม่เปลี่ยน, native Ada UI อ่านสมาชิกสามรายและคะแนน12/1/0ตรง SQL

ยังไม่ผ่านการพิสูจน์สำหรับงานเต็มนี้:

- Sandbox worker จำกัด1,000สมาชิก แต่ข้อมูลจริง1,438; ต้องใช้ pagination/checkpoint แทนการเปลี่ยนเพดานหรือดึงทั้งฐานทุก30วินาที
- Sandbox worker ยังไม่ซิงก์ purchase history; ต้องเพิ่มเส้นทาง import/อ่านประวัติแยกจากการให้แต้ม ไม่พึ่งแค่ claim/award เดิม
- ยังไม่มี live Supabase writer หรือบัญชี production Ada ที่จำกัดเฉพาะการเขียนที่อนุญาต ชุดทดสอบปัจจุบันไม่ใช่ตัวที่เปลี่ยนชื่อฐานแล้วเปิดจริงได้
- ต้องซ้อมนำเข้าข้อมูลจริงครบชุดในสำเนา และเทียบจำนวน/รหัส/บรรทัด/ยอด/วันเวลา รวมบิลคืนและ orphan; ทดสอบซ้ำและ restart ต้องไม่เพิ่มคน/บิล/แต้มซ้ำ
- ต้องตรวจการมองเห็นจากหน้ารายชื่อ/ประวัติของ SCCRM จริง และไม่ให้การนำเข้าข้อมูลติดต่อเป็นการยืนยันบัญชีหรือสิทธิ์เข้าดูประวัติโดยอัตโนมัติ

เกณฑ์เปิดจริง: ผลเทียบทั้งชุดผ่าน, สองหน้าจอแสดงเจ้าของประวัติตรงกัน, replay/restartไม่ซ้ำ, ขอบเขต writer จำกัด, มี journal ย้อนการเปลี่ยนเฉพาะที่ระบบซิงก์ทำได้ โดยไม่ลบข้อมูลเก่า ช่วงเริ่มต้นควรนำ Ada -> Supabase ก่อน แล้วเปิดส่งกลับเฉพาะ field ที่ผ่านทดสอบ

เอกสารนี้เป็นขอบเขตและผลสำรวจ ไม่ใช่คำยืนยันว่าเปิด live sync แล้ว บริการที่เครื่อง000ยังอยู่ sandbox เดิม ไม่มีการลด guard ไม่มี production writes และไม่มี commit/push
